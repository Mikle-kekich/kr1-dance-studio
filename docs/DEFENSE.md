# Шпаргалка к защите КР №1 — танцевальная студия (вариант 89)

Преподаватель может спросить любого участника команды о любой части проекта. Ниже — что показать и что ответить.

## 1. Порядок демонстрации (7–10 минут)

1. **Запуск** `run.bat`: видно `Соединение установлено`, затем главное меню.
2. **9 «Вывести таблицы базы данных»** — три связанные таблицы; 8 клиентов, 10 занятий, 16 записей во всех четырёх статусах.
3. **3 → 1** (записи) и **3 → 2 → 1** (карточка записи с клиентом и занятием: это JOIN).
4. **Создание записи (3 → 3)** и все проверки:
   * клиент 3, занятие 9, оплачено «да» — запись создана;
   * те же данные ещё раз — «уже записан» (БП-6);
   * клиент 6 (14 лет) на занятие 8 (18+) — «не подходит по возрасту» (БП-5);
   * занятие 7 — «нет свободных мест» (БП-7); занятие 1 — «уже началось или прошло» (БП-4);
   * клиент 999 — «Клиент с ID 999 не найден» (БП-3).
5. **Смена статуса (3 → 5)** для новой записи: «Завершена» — отказ со списком разрешённых статусов (БП-11); «Подтверждена» — успех; «Завершена» ещё раз — «занятие ещё не началось» (БП-13).
6. **Ошибка ввода:** в вопросе «Введите ID» набрать `abc` — `Ошибка: ID должен быть целым числом.`, вопрос повторяется; программа не падает.
7. **Изменение (3 → 4) и удаление (3 → 6)** с подтверждением: запись «Завершена» удалить нельзя (БП-14); отменить и удалить свежую запись — можно.
8. **Поиск (4):** `иван` (без учёта регистра), `кузнецов`, дата занятия, комментарий; **фильтры (5)** и **сортировка (6)**.
9. **Статистика (7)** — 15 показателей. **Экспорт (8 → 1)** — открыть файл из `export/` в Excel: 4 листа.
10. **Ошибка подключения:** `set DB_URL=jdbc:postgresql://localhost:5999/dance_studio` и запуск — понятное сообщение и вопрос «Повторить попытку подключения?».

## 2. Назначение основных классов

| Класс | Что делает |
|---|---|
| `Main`, `Application` | точка входа и «сборка» приложения: репозитории → сервисы → меню (зависимости передаются через конструкторы) |
| `DatabaseBootstrap` | проверка соединения, создание базы, таблиц и тестовых данных при первом запуске |
| `ui.*Menu`, `ConsoleInput`, `Printer` | только вывод меню, чтение ввода и печать таблиц; ни SQL, ни бизнес-правил |
| `service.*Service`, `EnrollmentRules` | бизнес-правила, проверки данных, поиск/фильтрация/сортировка, статистика, экспорт |
| `repository.Jdbc*Repository` | SQL-запросы через JDBC; `JdbcSupport` — общий код (соединение, `PreparedStatement`, `ResultSet`) |
| `model.*` | `Client`, `DanceClass`, `Enrollment`, перечисления, `Statistics` |
| `util.*` | `DatabaseManager` (соединения), `ExcelExporter`/`CsvExporter`, `TablePrinter`, `SqlErrors` |

## 3. Объектно-ориентированные приёмы

* **Инкапсуляция.** Поля классов `private`, доступ через методы. Сущности не проверяют данные сами: правила зависят от других объектов (БД, текущего времени), поэтому проверки собраны в сервисах.
* **Интерфейсы.** `CrudRepository<T>` (+ `ClientRepository`, `DanceClassRepository`, `EnrollmentRepository`), `Exportable`, `Menu`. Сервис зависит от интерфейса репозитория, поэтому в тестах JDBC-репозитории заменяются хранилищами в памяти — 69 тестов идут без базы данных.
* **`enum`.** `EnrollmentStatus` (со своими методами `allowedNext`, `canTransitionTo`, `isFinal`, `occupiesSeat`), `DanceStyle`, `DanceLevel`, `EnrollmentSortField` (компаратор внутри каждой константы). В БД хранится имя константы (`name()`), пользователю показывается русская подпись (`getLabel()`); в схеме есть `CHECK` на допустимые значения.
* **Полиморфизм.** (1) `BaseEntity.getShortDescription()` переопределён в `Client`, `DanceClass`, `Enrollment`; (2) `MainMenu` вызывает `run()` у объектов типа `Menu`, не зная, какое именно меню откроется; (3) `ExportTable.of(...)` принимает любые `Exportable` (`toExportRow()`); (4) `CrudRepository` имеет JDBC-реализации и in-memory реализации в тестах; (5) `JdbcSupport<T>` — шаблонный метод, наследники реализуют `mapRow`.
* **Коллекции.** `List` (списки сущностей), `Map` (`EnumMap` для счётчиков по статусам, `HashMap` для занятых мест, `LinkedHashMap` для статистики), `Set`/`EnumSet` (`allowedNext`), `Optional` (`findById`). Stream API: `filter`, `sorted`, `groupingBy`, `max`, `average` в `EnrollmentQueryService` и `StatisticsService`.
* **Исключения.** Иерархия от `DanceStudioException`: `BusinessException`, `EntityNotFoundException`, `DatabaseException`, `InvalidInputException`, `ExportException`. Ловятся в одном месте — `AbstractMenu.execute` — и превращаются в сообщение; `UserCancelledException` и `InputClosedException` — служебные.

## 4. JDBC

* **Как работает.** `DatabaseManager.getConnection()` открывает `Connection` через `DriverManager`; репозиторий готовит `PreparedStatement` с параметрами `?`, заполняет их (`setLong`, `setString`, `setObject`), выполняет `executeQuery()` / `executeUpdate()`, читает `ResultSet` и превращает строку в объект (`mapRow`). Всё в `try-with-resources` — соединение, запрос и результат закрываются автоматически, даже при ошибке. Весь этот код собран один раз в `JdbcSupport`.
* **ID новой записи** возвращается через `prepareStatement(sql, new String[] {"id"})` и `getGeneratedKeys()`.
* **Пароль** к базе не в коде: `database.properties` или переменные окружения `DB_URL`, `DB_USER`, `DB_PASSWORD`.
* **Ошибки SQL.** `SQLException` ловится в репозитории и превращается в `DatabaseException`/`BusinessException` (`SqlErrors`, по коду SQLSTATE): нет соединения (`08…`), неверный пароль (`28P01`), нет таблиц (`42P01`), нарушено ограничение (`23…`).

### Statement и PreparedStatement

| | `Statement` | `PreparedStatement` |
|---|---|---|
| SQL | строка целиком, значения вклеиваются конкатенацией | шаблон с `?`, значения передаются отдельно |
| Безопасность | уязвим к SQL-инъекции | значения не могут изменить структуру запроса |
| Скорость | запрос разбирается каждый раз | план запроса можно переиспользовать |
| Типы | значения надо самому превращать в текст (даты, числа) | `setDate`, `setBigDecimal`, `setObject` |

Пример инъекции: при `"... WHERE email = '" + email + "'"` ввод `' OR '1'='1` вернёт всех клиентов, а `'; DROP TABLE clients; --` может удалить таблицу. С `WHERE email = ?` такой ввод — просто необычная строка. В проекте `Statement` используется только для DDL (`CREATE DATABASE`, запуск SQL-скрипта), где параметров нет, а имя базы проверено регулярным выражением.

## 5. Связи между таблицами

```
clients 1 ---- N enrollments N ---- 1 dance_classes
```

* `enrollments.client_id → clients.id` и `enrollments.class_id → dance_classes.id` — внешние ключи (`ON DELETE RESTRICT`: нельзя удалить клиента или занятие, у которых есть записи);
* `enrollments` — таблица связи «многие ко многим» с собственными атрибутами: статус, цена, оплата, комментарий;
* ограничения: `PRIMARY KEY`, `FOREIGN KEY`, `NOT NULL`, `UNIQUE` (телефон, email), `CHECK` (статус, стоимость, диапазоны), частичный `UNIQUE INDEX (client_id, class_id) WHERE status <> 'CANCELLED'`.

## 6. Бизнес-правила и CRUD

Список из 18 правил и место в коде — в `README.md`. Правила находятся в сервисах, а не в меню; кроме того, часть продублирована ограничениями БД (последний рубеж защиты).

* **Создание:** `EnrollmentService.create` — БП-3…БП-8. **Изменение:** `update` (БП-9, БП-10) и отдельно `changeStatus` (БП-11…БП-13). **Удаление:** `delete` (БП-14) с подтверждением в меню. **По ID:** `getById` бросает `EntityNotFoundException`.
* **Почему статус меняется отдельно:** у смены статуса свои правила (переходы, оплата, время занятия).

## 7. Поиск, фильтрация, сортировка, статистика, экспорт

* **Поиск** — SQL в репозитории: `ILIKE ?` с параметром (без учёта регистра); служебные символы `%` и `_` в тексте экранируются (`SqlUtil.containsPattern`).
* **Фильтрация** — Stream API в `EnrollmentQueryService`: `findAll().stream().filter(предикат)`.
* **Сортировка** — `Comparator` внутри `EnrollmentSortField`; для ФИО используется `Collator` с русской локалью (правильный порядок букв, включая «ё»).
* **Статистика** — часть считает БД (`COUNT`, `SUM`, `AVG`, `GROUP BY` в `EnrollmentRepository`), часть — Java (`StatisticsService`: `groupingBy`, `max`, `average`).
* **Экспорт** — `ExportService` собирает `ExportTable` из данных БД; `ExcelExporter` (Apache POI) пишет `.xlsx` (листы, заголовки, форматы дат и денег, фильтры, закрепление первой строки); `CsvExporter` — CSV в UTF-8 с BOM и разделителем `;`.

## 8. Частые вопросы

* **Почему `RuntimeException`, а не проверяемые?** Ошибки обрабатываются на верхнем уровне меню; иначе каждый метод слоёв пришлось бы объявлять с `throws`.
* **Почему отдельный класс `EnrollmentRules`?** Чтобы `EnrollmentService` только координировал шаги, а правила читались списком; каждое правило — один метод.
* **Как проверялась работа?** 69 модульных тестов (`mvn test`) и ручной прогон всех пунктов меню на PostgreSQL 17, включая ошибки ввода и недоступную базу.
* **Что хранится в БД, а что нет?** В БД — все данные и ограничения; в коде — правила, зависящие от времени и связей между таблицами.
* **Что расширится в следующих КР?** Та же БД и модель используются в КР №2 (JavaFX), КР №3 (Spring + REST) и КР №4 (Android); слои `service` и `repository` переносятся практически без изменений.
